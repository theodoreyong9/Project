Experiments toward an AI-native social coordination infrastructure.

Six separate architectures exploring how humans and autonomous agents might create, represent, discover, execute and exchange value without requiring a single application or a single central authority.

The projects are deliberately separate. Each isolates a different coordination primitive and tests it under real technical constraints: locality, limited connectivity, latency, independent progression, semantic ambiguity and the absence of central coordination.

01 / SIX ARCHITECTURES

Six coordination primitives.

Each project explores a different primitive. They are not modules of a single application and are not intended to become one monolithic platform.

01 — Personal agency

Jobber

Primitive: personal interoperable agency

A local-first P2P coordination environment for human opportunities. The individual keeps agency locally while discovery and matching happen between directly connected peers.

Architecture
Local identity → IndexedDB → Local matching → P2P discovery → Human action
  • No backend or central database.
  • Browser ECDSA identity.
  • IndexedDB for local persistence.
  • WebRTC P2P transport through Trystero.
  • Local matching algorithm.
  • Optional local WebLLM intelligence when supported.
  • Research artifacts retain provenance and can be exported.
  • Two tabs or devices can be used to test P2P behavior.
Namespaces
  • Employment: Candidate / Recruiter. Candidate cover letters remain private until explicitly shared. Candidate and recruiter keywords are extracted from their actual documents or job descriptions.
  • Business: Offer / Client, including rate versus budget-range matching.
  • Independant: Service / Utilisateur, with self-declared LinkedIn URL on the service side.
  • Annonce: Seller / Buyer, with client-side image resizing.
  • Dating: reciprocal profiles and matching; the final score is constrained by the weaker direction.
  • Intelligence: ordered Build / Critic chains where participants explicitly request and obtain a position.
Other mechanisms
  • Explicit human-in-the-loop actions.
  • Local test matching without a network.
  • Research discovery only among directly connected peers.
  • No central research directory.
  • Chat persistence keyed by stable identity.
  • Attachment offer / accept handshake.
  • Canonical message IDs for synchronization.
  • Full identity/profile/blocklist/research backup and restore.
  • Optional Agent mode as a cross-namespace matcher.
  • Optional Near mode using opt-in geolocation and radius.

02 — Collective representation

SGD

Primitive: collective semantic representation

Semantic Graph Democracy explores collective representation through an AI-mediated graph rather than a binary vote.

Core idea

A submission is simultaneously a search operation, a navigation operation and a participation operation in the collective graph. There is no conventional for / against button.

Architecture
User text → Local semantic parsing → Issue → GitHub Action → Canonical graph
  • Static browser architecture.
  • WebLLM provides local semantic parsing preview.
  • Search is embedding-assisted.
  • Publication can use a prefilled GitHub issue or optional Device Flow OAuth.
  • GitHub Actions perform server-side semantic extraction from the submitted text.
  • The canonical key is determined server-side rather than by the client.
  • Invalid submissions are closed.
  • Valid submissions update graph JSON and are committed.
Security / anti-gaming properties
  • Issue bodies are treated as data.
  • Semantic fields and canonical keys are not client-authoritative.
  • No third-party code is executed by CI.
  • Repeated occurrences of the same canonical proposal have diminishing return, approximately 1/n.
  • Direct OAuth publication and prefilled issue publication use the same issue-body representation.
Current limits
  • Diversity structure is not yet implemented.
  • The domain remains a fixed enum.
  • There is no true subject-level graph yet.
  • Sybil resistance through reformulation remains open.
  • No human uniqueness proof.
  • Graph rendering is currently O(n²).
  • Embedding JSON remains relatively bulky.

03 — Permissionless execution

YourMine

Primitive: permissionless execution

A permissionless WebOS where applications and interface themes are published as ordinary files and can evolve through a distributed registry.

Core model
  • Spheres are applications.
  • Themes are interface layouts.
  • Both are plain files hosted through GitHub forks.
  • Distribution is ordered by participatory scoring rather than editorial selection.
Runtime
index.html → theme → desk.js → app.js → sphere
  • index.html boots the environment.
  • The selected theme is fetched and injected.
  • desk.js provides the desktop runtime.
  • app.js manages sphere lifecycle, P2P, PWA and profile functionality.
  • Source modules cover mining, building, lists and profiles.
  • Registries are represented through files.json and themes-files.json.
Scoped agency

Each sphere receives a scoped context ctx rather than unrestricted access to the global runtime.

  • Scoped storage.
  • Scoped UI.
  • Scoped profile access.
  • Scoped P2P operations.
  • Scoped navigation.
Registry progression

Publication follows a participatory score rule:

(score_now + 1) / (laps_now + 1) > (score_last + 1) / (laps_last + 1)

  • The first publication is always allowed.
  • A new sphere must improve the ratio.
  • Updates to an existing sphere require ownership.
  • The score is frozen at merge.
  • Ranking is based on score and laps.
  • There is no editorial override.
Interplanetary Proof of Will

Earth monetary systems assume communication latencies that become problematic between planets. A round trip between Earth and Mars can take minutes, making permanent global consensus impractical.

Proof of Will therefore explores a geographically independent form of participation: mining where you are, with who you are, without requiring global synchronization beyond the passage of time itself.

04 — Partitioned global coordination

AIWA Chain

Primitive: locally progressing value

A protocol experiment for value progression and transaction validation across independently progressing domains.

Starting point

Two wallets, one identity. A Solana keypair activates a real, irreversible burn — the Ignition — which requires genuine internet access to Earth's Solana network.

The same identity can then accrue native AIWA locally based on elapsed progression, without relying on a shared clock or requiring further network access.

Architecture
Solana identity → Ignition → Local progression → Accrual → Transfer → Mirror
  • Sequential-delay progression.
  • Value accrual based on progression.
  • Conservation of transferred value.
  • Mirror / reception layer.
  • Weighted Causal Tick.
  • Relative-rate mechanisms.
  • Optional P2P signaling through Trystero / Nostr.
Progression

Progression is tied to real sequential computation through a verifiable delay function rather than a shared calendar clock. This is intended to permit independent Earth / Mars progression without requiring the two domains to agree continuously.

Implementation
  • JavaScript reference implementation.
  • Rust implementation matching specified primitives byte-for-byte.
  • Modules include units, domain identity, event DAG, VDF, progression, reward, accrual, conservation, identity cost, hardware attestation, mirror, causal tick and wallet.
  • Contract registry and synchronization protocol are included as experimental components.
Honest limits
  • Initial Solana activation remains dependent on an Earth-hosted RPC.
  • Current activation uses devnet.
  • Browser / P2P testing has practical limits.
  • Transport between independent economies remains unresolved.
  • A real exchange rate between separate economies is not solved by the protocol.

05 — Capability discovery

Smartank

Primitive: AI-native capability discovery

An AI Navigator for Hugging Face: describe what you want to build, let local AI structure the intent, search the real catalog, rank candidates and explain the result.

Architecture
User intent → CPU taxonomy → Local WebLLM → HF API → CPU ranking → Local synthesis
  • 100% vanilla HTML / CSS / JavaScript.
  • No framework, bundler or build system.
  • Local WebLLM / WebGPU for reasoning.
  • Only the public Hugging Face API is used for catalog search.
  • CPU-first design: GPU inference is used only where it adds value.
Reasoning model

The LLM is deliberately not treated as a catalog that already knows the available models. It structures the user's intent, searches the real catalog, and reasons over retrieved candidates.

  • Deterministic CPU taxonomy identifies the initial task.
  • WebLLM confirms or corrects the task and extracts material, language and priorities.
  • Hugging Face search uses task and reinforcement queries.
  • CPU pruning and ranking reduce the candidate set.
  • WebLLM synthesizes an explanation only from real candidates.
  • ExplorerView receives structured JSON.
Failure behavior
  • If local synthesis is inconsistent or hallucinatory, the system can fall back to deterministic ranking.
  • When too few candidates are found, neighboring tasks can be searched automatically and the broadening is explicitly disclosed.
  • Composite objectives can become a capability pipeline.
Privacy

Reasoning stays local. Only derived search keywords are sent to the public Hugging Face API.

06 — Reflexive value architecture

ARVT

Primitive: reflexive value formation

ARVT explores value as the residue of a relation whose cost is real and whose sustainability is maintained. The architecture is a living philosophical corpus that evolves through sequential visitor contributions arbitrated by an LLM.

The proposition

« La valeur est le résidu d'une relation dont le coût est réel et la soutenabilité maintenue. »

ARVT is not simply a conventional application layer and it is not merely the theory sitting above the other architectures. It is a peer architecture in its own right.

Technical architecture
Visitor → Graph node → Question → Proposal queue → 2 proposals → Synthesis → New residue
  • GitHub Pages static interface.
  • Gun.js provides the living P2P corpus and graph.
  • No application server.
  • No central database.
  • GitHub Actions snapshot the corpus every six hours.
  • Persistent artifacts include corpus.md, graph.json and snapshot history.
Contribution cycle
Visitor arrives → Selects node → Asks question → Proposal enters queue → Two proposals → Synthesis → Corpus extension → Node densification
Graph and reflexivity

The graph currently includes concepts such as residue, relation, irreversibility and sustainability.

Node density reflects the number and history of syntheses. The model directs subsequent contributions toward less-dense nodes. This creates a gradient of exploration that follows the theory itself.

Guidance by gradient, conforming to the theory: the mechanism used to evolve the corpus becomes part of what the corpus theorizes.

This is the reflexive closure: the architecture does not merely describe the concept of value; its own operation becomes an instance of the relation it is attempting to understand.

02 / MAP

Different problems, related direction.

The architectures are intentionally orthogonal. Together they form a set of experiments around agency, representation, execution, value, discovery and reflexive evolution.

Jobber

How can an individual expose needs and opportunities without surrendering agency to a central platform?

SGD

How can collective intent be represented semantically rather than reduced to binary voting?

YourMine

How can execution and application distribution remain permissionless?

AIWA

How can value progress when domains cannot maintain continuous global consensus?

Smartank

How can AI discover capabilities from a real external catalog without pretending to know the catalog by heart?

ARVT

How can an architecture evolve through the same relation it is attempting to theorize?

03 / SYSTEM VIEW

From individual agency to collective coordination.

There is no requirement that the six systems become one product. Their relationship is conceptual: each isolates a mechanism that becomes relevant when centralized coordination becomes expensive, fragile or impossible.

Personal agency → Collective representation → Permissionless execution → Locally progressing value → Capability discovery → Reflexive evolution

The common question is not “how do I build another application?” It is closer to: what primitives are required for people, applications and autonomous agents to coordinate when there is no single system that can see, decide and control everything?

04 / PRINCIPLES

Constraints are part of the design.

The projects deliberately work with constraints instead of hiding them behind infrastructure.

Local agency

Keep identity, reasoning, data or progression as close to the participant as possible.

No permanent central authority

Central services may appear where unavoidable, but they should not become the conceptual source of truth for the whole system.

Explicit trust boundaries

Identity, permissions, provenance, publication and synchronization are treated as separate concerns.

Real constraints

Offline operation, latency, disconnected domains, limited compute, browser restrictions and ambiguous semantics are treated as architectural inputs.

AI as participant

AI is explored not only as a coding assistant but as a mechanism for semantic interpretation, capability discovery, critique, synthesis and coordination.

Graceful failure

When AI or connectivity fails, deterministic or local mechanisms should remain useful whenever possible.

05 / DEVELOPMENT METHOD

Built in dialogue.

The development process is itself part of the experiment.

Three-way dialogue

Me + ChatGPT + Claude

This project is developed through an ongoing three-way dialogue between myself, ChatGPT and Claude.

The models are not treated simply as coding assistants. They are used as counterparts for exploring ideas, challenging assumptions, testing architectural coherence, writing and reviewing implementations, and pushing concepts toward something executable.

The resulting architectures are therefore also experiments in AI-native research and development: the development process itself becomes part of the experiment.

06 / REFLEXIVITY

ARVT is a peer architecture — and a closure.

ARVT is deliberately not presented as a superior layer above the other projects.

The architecture

Visitor → question → semantic node → proposal → queue → composition of two proposals → synthesis → new residue → densified graph → next contribution.

This is a concrete technical flow, implemented through a static interface, Gun.js and periodic snapshots.

The reflexivity

The system's mechanism for deciding where the next contribution should go is derived from the conceptual structure it is producing.

Architecture becomes part of the theory. The theory becomes a constraint on the architecture.

07 / STATUS

Working experiments, not finished products.

The implementations are deliberately concrete, but the larger architectures remain research experiments. Known limitations are part of the documentation rather than something to hide.

Current approach

Small, independently deployable experiments. Prefer plain browser primitives, local computation and simple distributed mechanisms where they are sufficient.

Avoid introducing infrastructure merely because it is familiar. Add complexity only when the architecture requires it.

What remains open

Sybil resistance, distributed identity, cross-domain exchange rates, richer semantic graphs, transport independence, uniqueness, scaling and stronger guarantees around autonomous coordination remain open research problems.

The goal is not to claim that these problems are solved, but to make the assumptions and mechanisms concrete enough to test them.
