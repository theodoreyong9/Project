01 / Six architectures

Six coordination
primitives.

Each project isolates a different mechanism. They are not modules of a single application — and they are not intended to become one.

01
Personal agency
Jobber
Personal interoperable agency

A local-first P2P coordination environment for human opportunities. The individual keeps agency locally while discovery and matching happen between directly connected peers.

Data flow
Local identity → IndexedDB → Local matching → P2P discovery → Human action
  • No backend or central database
  • Browser ECDSA identity
  • WebRTC P2P transport through Trystero
  • Local matching algorithm
  • Optional local WebLLM intelligence
  • Full identity / profile / blocklist / research backup
  • Optional Agent mode as cross-namespace matcher
  • Optional Near mode via opt-in geolocation
Namespaces
  • Employment — Candidate / Recruiter. Cover letters private until shared.
  • Business — Offer / Client, rate vs budget-range matching.
  • Independent — Service / Utilisateur.
  • Annonce — Seller / Buyer, client-side image resizing.
  • Dating — Reciprocal profiles; score constrained by weaker direction.
  • Intelligence — Ordered Build / Critic chains.

02
Collective representation
SGD
Collective semantic representation

Semantic Graph Democracy explores collective representation through an AI-mediated graph rather than a binary vote. A submission is simultaneously a search, a navigation and a participation operation.

Data flow
User text → Local semantic parse → Issue → GitHub Action → Canonical graph
  • Static browser architecture
  • WebLLM local semantic parsing preview
  • Embedding-assisted search
  • Canonical key determined server-side
  • Repeated occurrences yield diminishing return ~1/n
  • Invalid submissions automatically closed
Known limits
  • Diversity structure not yet implemented
  • No Sybil resistance through reformulation
  • Graph rendering currently O(n²)

03
Permissionless execution
YourMine
Permissionless execution

A permissionless WebOS where applications and interface themes are published as ordinary files and evolve through a distributed registry ordered by participatory scoring.

Runtime
index.html → theme → desk.js → app.js → sphere
Registry progression
(score_now + 1) / (laps_now + 1)
> (score_last + 1) / (laps_last + 1)
  • First publication always allowed
  • New sphere must improve the ratio
  • Updates require ownership proof
  • No editorial override
Scoped agency per sphere
  • Scoped storage, UI, profile access, P2P, navigation
  • No unrestricted access to global runtime

04
Partitioned global coordination
AIWA Chain
Locally progressing value

A protocol experiment for value progression and transaction validation across independently progressing domains — including the latency constraints of interplanetary distance.

Data flow
Solana identity → Ignition → Local progression → Accrual → Transfer → Mirror
  • Sequential-delay progression via verifiable delay function
  • Value accrual based on local progression, not shared clock
  • Conservation of transferred value
  • JS reference + Rust implementation matching byte-for-byte
  • Optional P2P signaling through Trystero / Nostr
Honest limits
  • Initial activation remains dependent on Earth-hosted RPC
  • Transport between independent economies unresolved
  • Real exchange rate between separate economies not solved

05
Capability discovery
Smartank
AI-native capability discovery

An AI Navigator for Hugging Face: describe what you want to build, let local AI structure the intent, search the real catalog, rank candidates and explain the result — without pretending to know the catalog by heart.

Reasoning pipeline
User intent → CPU taxonomy → WebLLM → HF API → CPU ranking → Synthesis
  • 100% vanilla HTML / CSS / JS — no framework or build system
  • CPU-first design; GPU only where it adds value
  • LLM structures intent; does not pretend to know the catalog
  • Fallback to deterministic ranking if synthesis is inconsistent
  • Composite objectives become capability pipelines
Privacy
  • Reasoning stays local — only derived keywords reach HF API

06
Reflexive value architecture
ARVT
Reflexive value formation

ARVT explores value as the residue of a relation whose cost is real and whose sustainability is maintained. A living philosophical corpus that evolves through sequential visitor contributions arbitrated by an LLM — where the mechanism for directing contributions is derived from the theory being built.

« La valeur est le résidu d'une relation dont le coût est réel et la soutenabilité maintenue. »
Contribution cycle
Visitor arrives → Selects node → Asks question → Proposal queue → Two proposals → Synthesis → Corpus extension → Node densification
  • GitHub Pages static interface
  • Gun.js provides the living P2P corpus and graph
  • No application server, no central database
  • GitHub Actions snapshot corpus every six hours
  • Persistent artifacts: corpus.md, graph.json, snapshot history
The reflexive closure

Node density reflects the number and history of syntheses. The model directs subsequent contributions toward less-dense nodes, creating a gradient of exploration that follows the theory itself. The architecture does not merely describe value — its operation becomes an instance of the relation it is attempting to understand.

02 / Map

Different problems,
related direction.

The architectures are intentionally orthogonal. Together they form experiments around agency, representation, execution, value, discovery and reflexive evolution.

Jobber

How can an individual expose needs and opportunities without surrendering agency to a central platform?

SGD

How can collective intent be represented semantically rather than reduced to binary voting?

YourMine

How can execution and application distribution remain permissionless?

AIWA

How can value progress when domains cannot maintain continuous global consensus?

Smartank

How can AI discover capabilities from a real external catalog without pretending to know it by heart?

ARVT

How can an architecture evolve through the same relation it is attempting to theorize?

Personal agency → Collective representation → Permissionless execution → Locally progressing value → Capability discovery → Reflexive evolution

The common question is not "how do I build another application?" It is closer to: what primitives are required for people, applications and autonomous agents to coordinate when there is no single system that can see, decide and control everything?

03 / Principles

Constraints are
part of the design.

The projects deliberately work with constraints instead of hiding them behind infrastructure.

⬡
Local agency

Keep identity, reasoning, data or progression as close to the participant as possible.

⊘
No permanent central authority

Central services may appear where unavoidable, but they should not become the conceptual source of truth for the whole system.

⊞
Explicit trust boundaries

Identity, permissions, provenance, publication and synchronization are treated as separate concerns.

⧖
Real constraints

Offline operation, latency, disconnected domains, limited compute and semantic ambiguity are architectural inputs, not problems to paper over.

◈
AI as participant

AI is explored not only as a coding assistant but as a mechanism for semantic interpretation, capability discovery, critique, synthesis and coordination.

⟳
Graceful failure

When AI or connectivity fails, deterministic or local mechanisms should remain useful whenever possible.

04 / Development method

Built in dialogue.

The development process is itself part of the experiment.

Three-way dialogue
Me + ChatGPT + Claude

This project is developed through an ongoing three-way dialogue between myself, ChatGPT and Claude.

The models are not treated simply as coding assistants. They are used as counterparts for exploring ideas, challenging assumptions, testing architectural coherence, writing and reviewing implementations, and pushing concepts toward something executable.

The resulting architectures are therefore also experiments in AI-native research and development: the development process itself becomes part of the experiment.

05 / Reflexivity

ARVT is a peer
architecture — and a closure.

Deliberately not presented as a superior layer above the other projects.

The architecture

Visitor → question → semantic node → proposal → queue → composition of two proposals → synthesis → new residue → densified graph → next contribution.

A concrete technical flow, implemented through a static interface, Gun.js and periodic snapshots.

The reflexivity

The system's mechanism for deciding where the next contribution should go is derived from the conceptual structure it is producing.

Architecture becomes part of the theory. The theory becomes a constraint on the architecture.

06 / Status

Working experiments,
not finished products.

Known limitations are part of the documentation rather than something to hide.

Current approach

Small, independently deployable experiments. Prefer plain browser primitives, local computation and simple distributed mechanisms where they are sufficient.

Avoid introducing infrastructure merely because it is familiar. Add complexity only when the architecture requires it.

What remains open

Sybil resistance, distributed identity, cross-domain exchange rates, richer semantic graphs, transport independence, uniqueness, scaling and stronger guarantees around autonomous coordination remain open research problems.

The goal is not to claim that these problems are solved, but to make the assumptions and mechanisms concrete enough to test them.
