03 / TECHNICAL ARCHITECTURE

The primitives are implemented, not only described.

Each repository explores a concrete mechanism for allowing coordination to remain possible under divergence: different implementations, identities, communities, interfaces and execution environments.

Architecture 01
Jobber
Personal Interoperable Agency

Jobber is deliberately local-first and backend-free. Identity is generated in the browser, data is persisted locally, peers communicate directly and matching happens locally.

Browser identity → IndexedDB → P2P / WebRTC → Local matching → AI assistance

WebLLM can provide local AI assistance when available, while research artifacts preserve provenance and can be exported.

Architecture 02
SGD
Semantic Graph Democracy

SGD treats a contribution as a semantic operation rather than a yes/no vote. A visitor submits text, the system identifies its semantic relation to the collective graph and integrates valid contributions into a canonical structure.

Submission → Semantic parsing → Graph navigation → Validation → Graph update

The browser can perform local semantic parsing with WebLLM. GitHub Actions performs the server-side extraction and canonical graph update, keeping the public repository as the coordination substrate.

Architecture 03
YourMine
Permissionless Execution

YourMine separates the runtime from the application. Spheres are applications; themes can replace the interface; the registry is maintained through the user's fork.

Fork → Modify → Publish → Score → Redistribute

There is no requirement for a central editorial authority to decide which implementation is legitimate. The ecosystem can recognize compatible implementations through participation and shared interfaces.

Architecture 04
AIWA Chain
Partitioned Global Coordination

AIWA experiments with value domains that progress independently. Progression is tied to real sequential computation rather than a globally shared clock.

Identity → Ignition → Local sequential progression → Accrual → Verifiable exchange

The same identity that activates the system can accrue native AIWA locally. Domains can therefore progress at their own pace; reconciliation provides an informational signal rather than forcing all domains onto a shared progression clock.

Architecture 05
Smartank
AI-native Capability Discovery

Smartank treats natural language as the discovery interface for capabilities. The user describes what they want to build; local AI interprets the intent and searches an actual external catalog.

Intent → Local AI interpretation → Catalog search → Ranking → Evidence

The current implementation focuses deliberately on a narrow problem: navigating the Hugging Face model ecosystem through local AI rather than pretending to already have a complete universal capability graph.

Architecture 06 / Reflexive
ARVT
Autonomous Relation Value Theory

ARVT has its own architecture. Its object is a living corpus whose content and semantic graph evolve through sequential contributions from visitors.

A visitor asks a question and associates it with a semantic node. The proposal enters a queue. Once two proposals are available, they are composed into a synthesis that extends the corpus and modifies the graph.

Visitor → Question → Semantic node → Proposal → Queue → 2 proposals → LLM synthesis → New residue → Graph densification

Technically, the architecture uses a static GitHub Pages interface, Gun.js for the living P2P corpus, a semantic graph and proposal queue, with GitHub Actions periodically producing snapshots.

Its distinctive mechanism is the feedback loop: graph density influences where future contributions are directed. Less dense nodes become preferred sites of extension. The architecture thus does not merely describe relational value; it continuously generates the conditions under which the theory evolves.

Why "reflexive"? ARVT is at the same architectural level as the other five projects, but it also operates on its own underlying premise. It is a theory implemented as a relational process for producing the continuation of that theory.
04 / DESIGN PRINCIPLES

Protocol-first, not product-first.

The objective is not to make everyone use the same application. The objective is to make coordination survive the existence of different applications.

Conventional pattern

One application → one community → one authority

This direction

Primitives → implementations → forks → communities → shared coordination

01 — Divergence is a feature

Implementations are expected to change. A fork can alter the interface, replace the AI, change the language, modify the execution environment or become the basis of a new community.

02 — Compatibility replaces authorization

An ecosystem does not need to approve every implementation. If independent implementations preserve the interfaces and invariants required for coordination, they can participate in the same coordination space.

03 — Local agency

Identity, computation, data and decision-making should move as close as possible to the actors who actually perform them.

04 — No monolithic dependency

The system should remain meaningful when one implementation, interface, AI model, community or economic context disappears and another replaces it.

05 — Open source as an architectural mechanism

Source code enables an implementation to be read, copied, modified, forked, independently operated and recombined. Giving up control can make the system larger than its original implementation.

06 — Value can be relational

ARVT provides the reflexive economic intuition running through the experiments: value can be understood as the residue of a relation whose cost is real and whose continuity remains sustainable.

05 / REFLEXIVITY

ARVT is not above the architecture. It is an architecture that acts on itself.

This distinction matters. ARVT should not be represented as "the theory behind the five architectures". It is a sixth technical experiment with a different property.

Theory ↔ implementation ↔ new theory
Relational value intuition → Visitor contribution → Semantic composition → New residue → Corpus evolution → New relational intuition ↻

The architecture becomes part of what it theorizes.

06 / OPEN SOURCE

The smallest useful primitive may matter more than the largest application.

The goal is to discover mechanisms that independent actors can adopt without first joining the same platform.

Source code makes an architecture forkable. Forkability makes divergence possible. Interoperability makes divergence composable.
  • Read the implementation.
  • Copy it.
  • Modify it.
  • Fork it.
  • Operate it independently.
  • Combine it with another implementation.
07 / CURRENT STATUS

Experiments, not a solved society.

These repositories are prototypes, reference implementations and theoretical software. Their value is partly in making assumptions explicit, testable and forkable.

Current direction Build coordination infrastructure that can survive divergence: different implementations, different communities, different interfaces, different agents and different economic contexts.
